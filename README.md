# AI Value Studio

## From AI ideas to business value

AI Value Studio is a standalone AI advisory and assessment product for turning business problems into prioritized, measurable AI use cases and generating client deliverables. It is not a governance platform.

It supports the full path:

```text
Business discovery → Use case definition → Value assessment → Readiness → Governance → Prioritization → Pilot → Scale
```

## What is included

- AI Use Case Canvas
- Business Value Scorecard
- AI Portfolio Matrix
- Executive AI Opportunity Brief
- Executive Brief and Pilot Charter (generated French Markdown/PDF); [AI Governance Plan](docs/architecture/ai-governance-plan-decision-packet.md) (planned generated advisory deliverable)
- Product brief and commercial packaging
- [Functional specifications](docs/FUNCTIONAL_SPECIFICATIONS_FR.md) for the Web wizard, assessment engine and document generation
- [Coding agent brief](docs/CODING_AGENT_BRIEF_FR.md) for the MVP implementation scope and acceptance criteria
- [Implementation plan](docs/IMPLEMENTATION_PLAN.md) for the execution framework and UI

## Positioning

AI Value Studio is the standalone AMOA and decision layer that helps organizations select the right AI opportunities before investing in technology. Its document generation has no external platform dependency.

Older framework and execution-model sections below describe historical repository assets, not governance-platform capabilities of the AVS product.

## Framework dimensions

Each use case is assessed across:

- business value;
- current friction;
- data readiness;
- technical feasibility;
- adoption potential;
- risk and governance.

## Commercial offers

### AI Value Discovery Sprint

A 1–2 week discovery to identify and qualify 5–10 AI opportunities.

### AI Portfolio & Business Case Assessment

A 3–5 week assessment to prioritize use cases, estimate value and build the roadmap.

### AI Pilot Activation

A 6–12 week engagement to turn one prioritized use case into an operational pilot.

## Desktop app

The repository includes a minimal Electron shell in `electron-app/` that loads the real static export generated by `web/out/`.

### Backend requirement

The desktop renderer is the same exported wizard as the web build:

- it hydrates and works fully offline for local draft storage and step navigation;
- the secured backend foundation now exposes identity/workspace routes at `http://127.0.0.1:8000/api/v1`; legacy unauthenticated `/api/projects`, `/api/wizard`, `/api/docs`, and `/api/kickstart` routes are not mounted anymore, so the web build must point `NEXT_PUBLIC_API_BASE_URL` at the versioned API during integration;
- the new static shell lifecycle UI lives under `/studio`, `/studio/workspace`, `/studio/program`, `/studio/use-case`, and `/studio/admin/members`, all using query-parameter metadata routes compatible with static export;
- start the backend separately if you want the secured identity/workspace API available inside Electron.

### Build and start

```bash
cd web
npm install
npm run build
npx playwright test

cd ../electron-app
yarn install
npm start
```

`npm start` copies the current `web/out/` export into `electron-app/renderer/` and then launches the local Electron binary with a hardened renderer (`contextIsolation: true`, `nodeIntegration: false`).

### Packaging limits

- No installer/bundler pipeline is configured yet; this Electron app is currently verified for local launch only.
- If you later add Electron Packager, Forge, or Builder, include the generated `electron-app/renderer/` folder in packaged resources so the exported Next files remain available at runtime.
- The web export must be rebuilt before packaging whenever the wizard UI changes.

## Execution Framework (AI Value Studio Framework)

This repository also includes an execution layer framework for building and governing AI agents in enterprise environments, focused on safe, value-driven automation with human oversight.

The execution framework implements a closed-loop agentic AI system with the following phases:

1. **Objective Setting** - Define goals under human supervision
2. **Information Observation** - Gather relevant data and context
3. **Multi-step Planning** - Create detailed action plans
4. **Governed Tool & Data Selection** - Choose approved tools and data sources
5. **Cross-system Execution** - Perform actions across integrated systems
6. **Outcome Verification** - Validate results against objectives
7. **Failure Recovery & Escalation** - Handle errors and exceptions
8. **Feedback Learning** - Improve future performance

## Développement local

1. **Prérequis**
   - Python 3.11
   - `uv`
   - Node.js 22
   - `npm`
2. **Configurer le backend depuis la racine du dépôt**
   ```bash
   uv venv --python 3.11 .venv
   uv pip install --python .venv/bin/python -e ".[dev]" -r backend/requirements.txt
   cp .env.example .env
   ```
   Le backend ne charge pas automatiquement `.env`. Avant de lancer `uvicorn`, exporte les variables explicitement :
   ```bash
   set -a
   . ./.env
   set +a
   cd backend
   ../.venv/bin/alembic upgrade head
   ../.venv/bin/python scripts/dev_seed.py
   ../.venv/bin/uvicorn app.main:app --reload
   ```
   Pour un smoke test HTTP réel :
   ```bash
   curl -fsS http://127.0.0.1:8000/health
   curl -fsS http://127.0.0.1:8000/ready
   ```
3. **Lancer le web Next.js**
   ```bash
   cd web
   npm ci
   npm run dev
   ```
   Pour le shell S3 en mode dev local, exporte aussi :
   ```bash
   NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000/api/v1
   NEXT_PUBLIC_AUTH_MODE=dev
   ```
4. **Validation locale**
   ```bash
   .venv/bin/pytest -q
   .venv/bin/ruff check .
   .venv/bin/pytest backend/tests -q --cov=app.security --cov-report=term-missing --cov-fail-under=90
   cd web && npm run typecheck && npm run lint && npm run build && npm run test:e2e
   ```
   Pour vérifier réellement les politiques RLS PostgreSQL, lance aussi les tests backend avec un PostgreSQL 16 jetable exposé via `POSTGRES_TEST_URL`.
5. **Repères de configuration**
   - Le modèle de variables est documenté dans [`.env.example`](.env.example).
   - `AUTH_MODE=dev` n'est accepté qu'en `APP_ENV=local|test`, avec `DEBUG=true`, une base SQLite ou de test, et des origines CORS loopback explicites.
   - `NEXT_PUBLIC_API_BASE_URL` pointe vers `http://127.0.0.1:8000/api/v1` pour cette slice; aucune migration de schéma n'est lancée au démarrage de l'application.
   - `CORS_ALLOWED_ORIGINS` doit rester une liste explicite d'origines loopback séparées par des virgules; les jokers sont refusés.
   - `DOCUMENT_STORAGE_PATH` doit pointer hors du repository; le backend refuse un chemin de stockage local situé dans le worktree et n'expose jamais de clé publique de téléchargement.
   - Le web utilise `npm` et `web/package-lock.json`; l'application Electron conserve `yarn.lock` comme référence et n'est pas modernisée dans cette slice.
